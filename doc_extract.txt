1. Executive Summary
This document is a full system-design pass over an e-commerce platform, presented the way it would be reviewed in a real engineering organization: first the High-Level Design (HLD) ΓÇö the big picture of services, data flow, and infrastructure ΓÇö then the Low-Level Design (LLD) ΓÇö the internal structure of one service in enough detail to actually implement it. Around that core, this guide covers the operational concerns that separate a toy demo from a production system: how Docker and Kubernetes package and run the services, how Apache Kafka moves events between them reliably at scale, how each service's database is modelled, and how the system is observed once it's live (logging, metrics, tracing, alerting).
1.1 Architecture Principles

One service owns each business capability and its data; other services integrate through APIs and domain events, never direct database access.
Checkout follows one canonical Saga: Order ΓåÆ Inventory Reservation ΓåÆ Payment ΓåÆ Order Confirmation ΓåÆ Fulfillment ΓåÆ Notification, with durable compensation and reconciliation.
Critical mutations are idempotent, database-to-event publication uses an outbox, and important consumers use inbox/deduplication.
Production readiness is measured through SLOs, business signals, capacity assumptions, security controls, tested recovery and safe deployment automation.
≡ƒÆí Convention used throughout: solid arrows in diagrams represent synchronous (request/response) calls; dashed arrows represent asynchronous, event-driven communication through Kafka; dotted arrows represent telemetry (metrics/logs) flowing to the observability stack.
2. High-Level Design (HLD)
High-Level Design answers one question: "What are the major moving parts, and how do they fit together?" It deliberately stays away from class names or SQL columns ΓÇö that's LLD's job (Section 3). HLD is what you'd sketch on a whiteboard in a design-review meeting.
2.1 Functional Requirements
Functional requirements describe WHAT the system must let a shopper, and the business, actually do ΓÇö independent of how it's built. Everything else in this document exists to satisfy this list under the constraints in Section 2.2.
≡ƒÆí FR-9 and FR-10 are easy to overlook because no shopper explicitly "asks" for them, but they are functional requirements in the same sense as FR-4 ΓÇö the system either behaves correctly under retries and redeploys, or it doesn't. Treating them as functional (not just "nice-to-have" reliability work) is why Sections 3.4, 10, and 11 exist at all.
2.2 Non-Functional Requirements
Non-functional requirements describe HOW WELL the system must do the above ΓÇö the quality attributes and constraints that shape every architectural decision in the rest of this document, even though a shopper never sees them directly.
≡ƒÆí Every NFR above maps to a specific mechanism described later, rather than being an aspiration: Availability ΓåÆ Section 10's circuit breakers and Section 12.6's PodDisruptionBudgets; Scalability ΓåÆ Section 12.2's HPA; Consistency ΓåÆ Section 9.5's Saga pattern; and so on. If a future requirement can't be traced to a concrete mechanism this way, that's a sign the design doesn't actually satisfy it yet.
2.3 Services in the System
The platform is decomposed into seven business services plus an API Gateway. Cart is an explicit capability because cart persistence, guest-cart merging and checkout preparation have their own lifecycle and consistency rules.

3.3 Order State Machine
The Order Service's core business rule is a state machine ΓÇö an order can only move forward through specific, valid transitions. Modeling this explicitly (rather than as a loose status string anyone can overwrite) prevents invalid states like a "shipped" order silently reverting to "pending."
3.4 Concurrency Control: What Happens When Requests Collide
This is one of the most common real-world questions, and the state machine in Section 3.3 doesn't answer it by itself: what actually happens when two requests hit the system at almost the same instant? There are two distinct scenarios, and this system handles them with two different techniques.
Scenario A: Two different shoppers buy the last unit of a product
Shopper A and Shopper B both click "Buy" on the last remaining unit within milliseconds of each other. Both requests reach separate pods of the Inventory Service (Figure 5) at nearly the same time.
The naive, broken approach reads the quantity, checks it in application code, then writes:

The fix is to never let application code decide based on a value it read a moment ago ΓÇö push the check INTO the same atomic SQL statement as the write, so the database's own row lock does the deciding:
Whichever request's UPDATE reaches Postgres first acquires a row lock on that stock_levels row; the second request's UPDATE simply waits until the first transaction commits, then re-evaluates quantity >= 1 against the now-updated value and correctly fails with rowCount = 0. Nothing in the application code has to know locking happened ΓÇö the database guarantees it.
Scenario B: The same shopper's checkout click fires twice
A slow network causes the browser to retry, or the shopper double-clicks "Place Order" before the button visually disables. This is NOT a stock race ΓÇö it's a duplicate-request problem, and it's solved differently: by the Idempotency-Key pattern (Section 11), not by database locking. The frontend (Section 4.5) generates one key per checkout attempt and sends the same key on both the original click and any retry, so the Order Service's idempotency check (Section 11.1) short-circuits the second request and returns the first request's result instead of creating a second order.
≡ƒÆí Rule of thumb used throughout this design: races between DIFFERENT requests for the SAME resource (two shoppers, one stock row) are solved with atomic SQL / row locks. Duplicate delivery of the SAME logical request (retries, double-clicks, at-least-once Kafka redelivery) is solved with idempotency keys. They look similar but need different fixes ΓÇö using idempotency keys alone would not stop two different shoppers from oversubscribing stock, and using row locks alone would not stop a single retried request from creating two orders.

Locking Strategies Used in This System
≡ƒÆí Postgres's default isolation level (READ COMMITTED) is sufficient for all three techniques above because each relies on row-level locking or a version check rather than on transaction-level snapshot guarantees. SERIALIZABLE isolation is deliberately avoided for hot paths like checkout ΓÇö it prevents anomalies none of these flows are exposed to, while adding serialization-failure retries the team would otherwise not need to handle.

3.6 API Versioning Strategy
The contract in Section 3.5 will change over time ΓÇö a new required field, a renamed key, a different validation rule. Without a versioning strategy, changing it breaks every client that hasn't updated yet, including the mobile app version still installed on shoppers' phones from six months ago.
Backward-compatible changes (adding an optional field, adding a new enum value a client can ignore) ship into the CURRENT version ΓÇö no version bump needed.
Breaking changes (removing a field, changing a field's type, changing required-ness) ship as a new version, with the old version kept running until client adoption data (tracked via the API Gateway's access logs) shows the old version's traffic has dropped to zero.
A deprecation is announced via a Deprecation and Sunset HTTP response header on the old version, giving consumers (including the team's own frontend, Section 4) a machine-readable countdown rather than an email that gets missed.
≡ƒÆí This system's Gateway routes /api/v1/* and /api/v2/* to different Kubernetes Service names (order-service-v1, order-service-v2), so both versions can run as separate Deployments and be scaled/rolled back independently during a migration window.

4.6 Authentication Storage & Browser Security
The frontend should treat the access token as short-lived and avoid persisting long-lived refresh tokens in localStorage. A safer browser model is an HttpOnly, Secure, SameSite refresh-token cookie, rotation on refresh, server-side revocation for suspicious sessions, and CSRF protection where cookie-authenticated requests are used.
The API client should never accept a client-calculated total as authoritative. Checkout sends item IDs and quantities; the backend derives price, discounts, taxes, shipping and final amount from server-owned data.
Network errors: TanStack Query's built-in retry (with backoff) handles transient failures automatically; a global error boundary catches anything unrecoverable and shows a friendly fallback instead of a blank screen.
Stale cache after payment: cap cache time (staleTime) tightly for anything price-related, and explicitly invalidate the product cache when a price-change event is pushed, so a shopper never checks out at a stale price.
Offline / flaky connections: mutations (like "place order") are guarded against double-submission by disabling the submit button on isPending and by the idempotency key described in Section 11 ΓÇö the frontend generates the key once per checkout attempt and reuses it on retry.
Race conditions: rapid quantity changes in the cart use TanStack Query's request cancellation (AbortController) so an old, slow response can't overwrite a newer one.

5. Monolith vs. Microservices: When & Why

≡ƒÆí Rule of thumb: most successful microservice systems started as well-organized monoliths and split only when specific services needed independent scaling, deployment cadence, or ownership. Splitting too early pays the distributed-systems tax with none of the payoff.
6. Decomposing a System: Domain-Driven Design Basics
6.1 Single Responsibility Principle (SRP)
A service should represent one business capability. If a service does two unrelated jobs (handling payments AND sending marketing emails), that's a signal it should be two services.
6.2 Bounded Context
The same real-world concept can mean different things in different services:
In Auth: a "User" holds a password hash, roles, and login history.
In Order: a "User" holds shipping addresses and order history.
Each service owns its own model shaped around what IT needs ΓÇö no shared "User" library across services.
≡ƒÆí Pitfall: a shared "models" package imported by every service quietly rebuilds a monolith, coupling every service to that package's release schedule.

7. Service Communication: Synchronous & Asynchronous
7.1 Synchronous (REST / gRPC)
Analogy: a phone call ΓÇö the caller waits for an answer. Used when an immediate response is required, e.g. a client fetching product details to render a page.
Production hardening for synchronous calls:
Timeouts on every outgoing call ΓÇö never wait forever.
Retries with exponential backoff + jitter for transient failures only (not for 4xx client errors).
Circuit breakers (Section 10) to fail fast once a dependency is clearly unhealthy.
7.2 Asynchronous (Event-Driven via Kafka)
Analogy: posting a notice on a public bulletin board ΓÇö the sender doesn't wait for, or even know, who reads it. The Order Service publishes an order.created event; Payment, Inventory, and Notification each consume it independently.
Production hardening for asynchronous consumers:
Idempotency: processing the same event twice (redelivery is normal) must not double-charge a card or double-send an email.
Dead-letter topics: events that repeatedly fail processing are moved aside for manual inspection instead of blocking the partition forever.

8. Apache Kafka Deep Dive
Kafka is the event backbone in Figure 1 ΓÇö the shared "nervous system" that lets Order, Payment, Inventory, and Notification react to each other without ever calling one another directly.
8.1 Why Kafka for This System
Throughput: an e-commerce platform during a sale can generate thousands of order events per second ΓÇö Kafka is built for this scale.
Replay: if the Notification Service ships a bug, it can be fixed and re-run from an earlier offset to resend missed notifications ΓÇö impossible with a queue that deletes messages after delivery.
Multiple independent consumers: new services (e.g., a future Analytics Service) can subscribe to order.created without the Order Service changing at all.

8.6 Schema Registry & Event Evolution
The Kafka examples above serialize events as plain JSON, which works but has no guardrail: nothing stops the Order Service from renaming a field and silently breaking every consumer that reads it. A schema registry (Confluent Schema Registry, or AWS Glue Schema Registry when using MSK) adds that guardrail.
Every event schema (e.g., OrderCreated v1) is registered centrally as an Avro or Protobuf schema, and the registry enforces a compatibility mode ΓÇö this system uses BACKWARD compatibility, meaning a new schema version must still be readable by consumers built against the previous version.
Allowed under BACKWARD compatibility: adding a new optional field with a default value. Rejected by the registry at publish time: removing a field, renaming a field, or changing a field's type ΓÇö the producer's deploy fails fast in CI rather than silently breaking Notification Service in production three services away.
Each message carries a small schema ID instead of the full schema, so the wire format stays compact ΓÇö consumers fetch the schema definition from the registry (and cache it) the first time they see a new schema ID.
≡ƒÆí Why not just JSON with a versioned event type field (as shown in Section 8.4's code)? That approach is simpler to start with and is what a small team should reach for first ΓÇö it's what this guide's code examples use for readability. A schema registry earns its operational overhead once enough independent teams/services produce and consume events that a human-reviewed convention is no longer enough to prevent accidental breaking changes.

8.7 Consumer Rebalancing & Delivery Semantics in Practice
Section 8.2 introduced consumer groups; this is what actually happens operationally when a consumer group's membership changes ΓÇö e.g., during a rolling deployment of the Payment Service (Section 12.4).
A new Payment Service pod starts up and joins the payment-service-group consumer group.
Kafka's group coordinator triggers a rebalance: partition ownership is reassigned across all group members (including the new pod), which briefly pauses consumption for the whole group.
Each consumer resumes reading from its newly assigned partition(s) starting at the last COMMITTED offset for that partition ΓÇö not from wherever the previous owner happened to be mid-processing.
If the previous owner had read a message but not yet finished processing it when the rebalance happened, that message gets redelivered to whichever consumer now owns the partition ΓÇö this is precisely the at-least-once redelivery case Section 8.5's idempotency check exists for.
This is also why this system deliberately does NOT rely on Kafka's exactly-once semantics (EOS) transactions for the order/payment/inventory event flow, even though Kafka supports them: EOS guarantees exactly-once processing WITHIN Kafka (producer to topic to consumer offset commit), but the moment a consumer's side effect leaves Kafka's transaction boundary ΓÇö charging a card via Stripe, sending an email ΓÇö EOS can no longer cover it. The idempotency-key pattern (Section 11) is the mechanism that actually has to hold at that boundary regardless, so this system invests there rather than in Kafka-level EOS configuration, which would add operational complexity without removing the need for Section 11's checks.

9. Database Design, Optimization & Selection Rationale
Section 6 established the rule: one database per service, never shared. This section makes that concrete with an actual schema, explains WHY each service picked its specific database technology, and covers the optimization techniques a real deployment needs at scale.
9.1 Database Selection Rationale
Every choice below trades something away ΓÇö the goal is picking the right trade-off per service, not one database for the whole system.
9.2 Order Service ΓÇö Entity Relationship Diagram

Figure 4 ΓÇö orders and order_items are written in one transaction alongside outbox_events, solving the dual-write problem described below.
9.3 The Dual-Write Problem & the Outbox Pattern
A subtle bug many teams hit: the Order Service saves the order to Postgres, THEN calls Kafka to publish order.created. What if the process crashes between those two steps? The order exists in the database, but the event was never published ΓÇö Payment and Inventory never find out.
The transactional outbox pattern fixes this: instead of publishing to Kafka directly, the service writes the event into an outbox_events table in the SAME database transaction as the order itself. A separate lightweight process (or Kafka Connect's Debezium connector) tails that table and publishes to Kafka. Since the order row and the outbox row are committed atomically, the event can never be "lost" relative to the order.
9.4 Query & Access-Pattern Optimization
Indexing: composite index on orders(user_id, created_at DESC) makes "a user's order history" ΓÇö the single most common Order query ΓÇö an index-only scan instead of a table scan.
Cache-aside for the catalog: the Product Service checks Redis first; on a miss it reads MongoDB and populates the cache with a TTL. A price or stock update explicitly invalidates the key rather than waiting for TTL expiry, so stale prices (flagged in Section 4.5) are minimized.
Read replicas: Order and Payment Postgres instances run with one or more read replicas; reporting/analytics queries and "get my order history" reads are routed to a replica, keeping the primary free for writes.
Connection pooling: PgBouncer sits in front of Postgres so hundreds of short-lived pod connections don't exhaust the database's native connection limit.
Avoiding N+1 queries: fetching an order with its items uses a single JOIN (or a batched IN query) in the repository layer, never a loop issuing one query per item.
Table partitioning: as the orders table grows, it's range-partitioned by created_at (e.g., monthly) so old-order archival and index maintenance don't lock the whole table.
Denormalized read models: the Order Service keeps a small denormalized copy of product name/price at order time (not a live join to the Catalog DB) ΓÇö this also correctly preserves historical pricing even after the product's price later changes.
9.5 Cross-Service Consistency: The Saga Pattern
Order Service creates order (PENDING) and publishes order.created.
Inventory Service atomically reserves stock and publishes inventory.reserved, or publishes inventory.rejected.
Payment Service consumes inventory.reserved, charges the customer, and publishes payment.completed or payment.failed.
On payment.failed, Inventory releases the reservation and Order moves to CANCELLED. Every reservation has a TTL/expiry path so stock cannot remain held forever if an event or consumer is lost.
≡ƒÆí This is a choreographed saga ΓÇö each service reacts to events with no central coordinator. Larger systems sometimes use an orchestrated saga instead (a dedicated Order Orchestrator service explicitly calling each step) when the workflow gets too complex to follow via events alone.


10. Error Handling & Cascading Failure Prevention
A distributed system fails in ways a monolith never does: one slow dependency can exhaust every caller's threads/connections and take the whole platform down with it ΓÇö a cascading failure. This section covers the specific techniques used to stop that, and why each one was chosen over the alternative.
10.1 API Gateway & Centralized Auth
The Gateway validates JWTs and enforces rate limits before a request reaches any internal service, so individual services can trust that anything reaching them already passed the gate, instead of every service re-implementing auth.
10.2 Timeouts, Retries & Backoff
Why chosen: a call with no timeout can hang a request thread indefinitely, and an unbounded retry can turn a brief blip into a self-inflicted traffic spike (a "retry storm") that makes the outage worse.
10.3 Circuit Breakers
Analogy: an electrical circuit breaker. If Payment starts failing repeatedly, a breaker (e.g. the opossum library) trips and fails fast instead of letting callers queue up waiting threads. After a cooldown, it allows a trial request through to check recovery.
Why chosen over just retrying: retries help with brief blips; a circuit breaker is for sustained outages, where continuing to retry would only pile up load on an already-struggling dependency and delay its recovery.
10.4 Bulkhead Pattern
Named after a ship's bulkheads, which stop one flooded compartment from sinking the whole vessel. Applied here: the Order Service uses a separate, size-limited connection pool/thread pool for calls to Payment vs. calls to its own database. If Payment is slow, it can only ever exhaust its OWN pool ΓÇö order reads/writes keep working normally.
10.5 Graceful Degradation & Fallbacks
Why chosen: for read paths, a slightly stale or reduced response is almost always better than a hard error page.
If the Product Service's live stock check times out, the page falls back to the last cached stock_hint (Section 9.1) with a "low confidence" flag, rather than failing the whole page load.
If Recommendations (a non-critical service) is down, the product page simply omits the "You may also like" section instead of failing the entire request ΓÇö this is why non-critical calls are made in parallel and awaited independently, not chained into the critical path.
10.6 Centralized Error Handling Middleware
5xx messages are deliberately generic to the client (never leak stack traces/internals) while the full error is logged server-side against the correlation ID.
4xx messages stay specific ("Item out of stock") because the client needs that detail to react correctly.
10.7 Distributed Tracing & Correlation IDs
The Gateway assigns every request an x-correlation-id. Every service's logger includes that ID, and it also rides along as a Kafka message header (Section 8.4) ΓÇö so one ID can trace a request across both synchronous hops and asynchronous event chains, and directly into the error-handler output above.
10.8 Network & Secrets Security
Traffic between pods is restricted using Kubernetes NetworkPolicies (e.g., only the Gateway may call Order Service directly).
Service-to-service traffic can be encrypted with mutual TLS via a service mesh (Istio/Linkerd) in larger deployments.
Credentials live in Kubernetes Secrets / AWS Secrets Manager (Section 13), never in the image or source code.

11. Idempotency Deep Dive: Payment APIs
This is the single highest-stakes correctness problem in the whole system: a network retry must never charge a customer twice. If a client calls POST /payments and the response is lost to a timeout (even though the charge actually succeeded on Payment's end), the client's natural reaction ΓÇö retry ΓÇö must be provably safe.
11.1 The Idempotency-Key Pattern
The client (frontend, Section 4.5) generates a unique Idempotency-Key (a UUID) once, before the first attempt at a given payment.
Every retry of that SAME logical payment reuses the SAME key ΓÇö this is the critical part; a new key per retry defeats the whole mechanism.
The Payment Service checks an idempotency_keys table for that key BEFORE processing: if found and completed, it returns the ORIGINAL stored response immediately, without charging again.
If the key is new, it processes the payment, stores the result against the key, and returns it.
If the key exists but is still IN_PROGRESS (a concurrent duplicate request arrived while the first was still processing), the second request is rejected with 409 Conflict rather than racing the first.

11.4 Exactly How Concurrent Duplicates Are Resolved at the Database Level
Section 11.3's note glossed over a subtlety worth spelling out fully, because it's the same class of race condition as Section 3.4: what if the SAME idempotency key arrives twice at almost the same instant ΓÇö not a slow retry seconds later, but truly concurrent, e.g., a client that fires the request and, 50ms later before any response arrives, fires an automatic retry?
Because idempotency_key is the PRIMARY KEY, Postgres enforces uniqueness at the storage engine level ΓÇö two concurrent INSERTs for the same key cannot both succeed, even if they arrive on different database connections at the exact same microsecond. 11.5 Layering On Top of the Payment Gateway's Own Idempotency
Stripe and PayPal both accept their own idempotency key on the charge call. The Payment Service's internal key (Section 11.2) and the gateway's key are complementary, not redundant: the internal key protects against the CLIENT retrying the call to the Payment Service; the gateway key additionally protects against the Payment Service itself retrying its own outbound call to Stripe (e.g., after a bulkhead-limited timeout in Section 10.4) without double-charging at the gateway level.

11.7 Payment Reconciliation & Refunds
Payment is a distributed boundary with an external system, so a periodic reconciliation job should compare Payment records, gateway transaction status and verified webhook events. Unknown outcomes should become REQUIRES_RECONCILIATION rather than being automatically retried as a new charge.
Refunds need their own idempotency key and lifecycle (REQUESTED ΓåÆ SUBMITTED ΓåÆ CONFIRMED / FAILED). A refund operation must be safe to retry and must never create two provider refunds for the same business reason.
Same key, different amount: treated as a client bug ΓÇö rejected with 422 (Section 11.3), never silently processed with either amount.
Key reused after expiry (>24h): treated as a brand-new payment ΓÇö this is why the expiry window must comfortably exceed any realistic client retry timeout.
Consumer crash mid-processing (status stuck IN_PROGRESS forever): a background sweeper job resolves keys stuck IN_PROGRESS past a short threshold (e.g. 2 minutes) by checking the actual gateway transaction status and correcting the row.
Webhook-driven confirmation arrives before the synchronous response: the webhook handler (Stripe calling back asynchronously) updates the SAME idempotency-keyed row rather than creating a second record, keyed by the gateway's own transaction reference.

12. Docker & Kubernetes: How They Fit
Docker and Kubernetes solve two different problems. Docker packages a single service into a portable, reproducible unit. Kubernetes runs, scales, and heals many of those units across a cluster of machines.
12.1 Docker's Role: Packaging
Every service (from the directory structure in Section 16) is built into its own container image via a multi-stage Dockerfile ΓÇö one stage installs dependencies and builds, a second, minimal stage runs the app, keeping the final image small.
Multi-stage build keeps the final image lean and runs as a non-root user (node) ΓÇö a basic production security practice.
12.2 Kubernetes' Role: Orchestration
Once each service is an image, Kubernetes takes over the operational concerns a monolith never had to think about: which machine runs which container, what happens when one crashes, and how many copies should be running right now.

12.5 Resource Sizing Methodology
The requests/limits numbers in Section 12.4 aren't guesses ΓÇö an admin arrives at them methodically, and re-checks them as traffic patterns change:
Start from load-test data (Section 14.6), not intuition: run the service under a representative load profile and record actual CPU/memory usage via Prometheus (Section 15.1).
Set requests to roughly the p50 (median) observed usage ΓÇö this is what the Kubernetes scheduler reserves for the pod on a node, so setting it too high wastes cluster capacity, and too low causes the scheduler to over-pack nodes.
Set limits to roughly the p99 observed usage plus headroom for traffic spikes ΓÇö this is the hard ceiling; a CPU limit throttles the pod's CPU time, while a memory limit that's exceeded gets the pod OOMKilled.
Re-run this exercise after any significant code change (a new dependency, a new code path) and on a recurring cadence (e.g., quarterly) as real production traffic patterns emerge ΓÇö initial sizing from a load test is a starting point, not a permanent setting.
12.6 Pod Disruption Budgets & Network Policies
Two more Kubernetes objects worth naming explicitly, since both directly prevent real incidents this system has to plan for.
Without a PodDisruptionBudget, a routine cluster operation ΓÇö draining a node for a Kubernetes version upgrade, or the cluster autoscaler scaling down ΓÇö could terminate 2 of Order Service's 3 pods simultaneously, leaving only 1 to absorb all traffic. The PDB tells Kubernetes "never let a voluntary disruption take availability below this line," and Kubernetes will delay the drain/scale-down until it can proceed safely.
≡ƒÆí Without this NetworkPolicy, Kubernetes' default is to allow all pod-to-pod traffic within the cluster ΓÇö meaning a single compromised or misbehaving pod could call any other service directly. Explicit NetworkPolicies turn that default off service by service, which is why Section 10.8 lists this as a security control rather than an optional hardening step.

13.8 IAM Roles & Workload Identity (EKS Pod Identity / IRSA)
A naive setup gives every pod the EKS node's IAM role, which means every service can call every AWS API the node can ΓÇö a Product Service pod could technically read Payment's secrets. IAM Roles for Service Accounts (IRSA) fixes this: each Kubernetes ServiceAccount gets its OWN narrow IAM role, assumed only by pods using that ServiceAccount, via the OIDC provider created in Section 13.7.
≡ƒÆí Why OIDC federation for CI instead of long-lived AWS access keys in GitHub Secrets? A long-lived key that leaks is valid until manually rotated; an OIDC-federated role issues short-lived credentials scoped to that specific workflow run, so a leaked credential expires in minutes rather than being a standing risk.

13.11 Disaster Recovery & Backup Strategy
Provisioning the infrastructure (Section 13.7) answers "how does this get built"; disaster recovery answers "what happens when part of it is destroyed." Every data store in Section 9 has an explicit backup and recovery plan ΓÇö "RDS backs itself up" is not a DR plan on its own until the recovery time and recovery point are stated and tested.
RPO (Recovery Point Objective) and RTO (Recovery Time Objective) are stated per store because they genuinely differ: losing 5 minutes of session cache is a non-event, while losing 5 minutes of Order/Payment writes is a serious incident ΓÇö the numbers above reflect that Postgres gets the tightest guarantees precisely because it holds the money- and stock-critical data identified back in Section 9.1.
Backups are tested, not just taken: a scheduled job restores the latest Order DB snapshot into an isolated environment and runs a smoke-test query monthly ΓÇö an untested backup is a hypothesis, not a guarantee.
Cross-region snapshot copies (RDS's automated cross-region snapshot copy) protect against a full region outage, not just an AZ failure, at the cost of the snapshot's copy lag becoming part of the effective RPO for that specific failure mode.

Everything in this guide so far describes a single-region, multi-AZ deployment ΓÇö the right starting point for most systems, since multi-AZ already protects against the far more common failure (a single data center/AZ issue) at a fraction of the operational cost of multi-region. ≡ƒÆí This system's recommended default is active-passive DR, not active-active: it delivers real resilience against the highest-impact failure (a region going down) without taking on active-active's cross-region consistency problem, which the Saga pattern (Section 9.5) already has to solve WITHIN one region and shouldn't have to solve across two at the same time.
13.13 AWS Reference Architecture: Control Plane, Data Plane and Trust Boundaries
The deployment is divided into three planes. This makes the AWS architecture easier to secure, scale and operate because each plane has a different trust model and failure domain.
ΓÇó Public edge: Route 53 ΓåÆ CloudFront/WAF ΓåÆ ALB. End users never connect directly to EKS nodes, pods, databases, Redis or Kafka brokers.
ΓÇó Application data plane: EKS services and workers access RDS, DocumentDB, Redis, MSK and SQS through private networking and explicit identities.
ΓÇó AWS management plane: EKS API, ECR, Secrets Manager, CloudWatch, CloudTrail and deployment tooling are administrative surfaces and should not share the same access path as shopper traffic.
ΓÇó External payment providers use controlled outbound connectivity. AWS API traffic should prefer VPC endpoints where supported, reserving NAT for true public-internet dependencies.

13.15 VPC, Subnets and Route Tables

Use a multi-AZ VPC with separate public, private-application and private-data tiers. The public tier contains only internet-facing load-balancers and controlled egress components; application and stateful resources stay private.
ΓÇó Size subnets for VPC CNI pod addresses as well as EC2 node addresses. A cluster can exhaust pod IPs before CPU becomes the scaling bottleneck.
ΓÇó Reserve unused CIDR space so a third AZ or an additional workload tier can be introduced without redesigning the VPC.
ΓÇó Use separate VPCs for production and non-production when the business impact of an accidental cross-environment connection is high; otherwise, enforce strict subnet, security-group and IAM isolation.

13.21 NAT, VPC Endpoints and Egress Strategy

Private workloads should use public internet egress only when necessary. NAT provides controlled IPv4 egress; VPC gateway/interface endpoints keep supported AWS service calls inside AWS networking and reduce NAT dependence.

ΓÇó Prefer S3 gateway endpoints and interface endpoints for AWS services such as ECR, Secrets Manager and Systems Manager when they are part of the workload path.
ΓÇó Define an external egress allowlist for third-party APIs, monitor egress bytes, and investigate new destinations as a security signal.
ΓÇó Evaluate Regional NAT Gateway when it materially simplifies HA and routing. Make the choice from actual egress requirements and cost, not from a default assumption.

14.4 Testing Strategy: The Test Pyramid
The "Lint + Unit Tests" box in Figure 8 hides a deliberately shaped set of test types ΓÇö deliberately more unit tests than integration tests, and more integration tests than end-to-end tests, because each layer up gets slower and more brittle.
≡ƒÆí The common anti-pattern this pyramid avoids: a suite dominated by end-to-end tests. They're the most realistic but also the slowest and the most likely to fail for reasons unrelated to the code change (a flaky network call, a timing issue) ΓÇö a large e2e suite becomes something engineers learn to ignore or re-run rather than trust, which defeats its purpose.
14.5 Contract Testing for Kafka Events
Unit tests catch bugs within the Order Service; they cannot catch "the Order Service renamed a field, and the Notification Service ΓÇö in a completely different repository ΓÇö will silently break in production." Contract testing (using a tool like Pact) closes that gap without requiring either service to run the other's code in CI.
The consumer (Notification Service) writes a contract test stating what it expects an order.created event to look like ΓÇö which fields it reads and their types ΓÇö and Pact generates a contract file from that expectation.
The contract file is published to a shared Pact Broker.
The producer (Order Service)'s CI pipeline fetches the latest contract from the broker and verifies its ACTUAL event output against it ΓÇö if Order Service's CI run fails this verification, the breaking change is caught in Order Service's own pull request, before it ever merges, let alone deploys.
This is deliberately the opposite direction of an integration test: instead of Notification Service testing against a real Order Service, Order Service tests against Notification Service's stated expectations ΓÇö which scales to many consumers without the producer needing to know about, or run, each one individually.
14.6 Load & Chaos Testing
CI's tests (Section 14.4) verify correctness. They say nothing about whether the system holds up under Black-Friday-level traffic, or recovers cleanly when a dependency actually fails ΓÇö two different, deliberately destructive kinds of testing that run outside the per-PR pipeline.
Load testing (k6 or Gatling): a scripted ramp-up simulating realistic checkout traffic is run against staging before major sales events, validating the resource sizing from Section 12.5 and the HPA thresholds from Section 12.2 against real numbers rather than estimates.
Chaos testing (AWS Fault Injection Simulator, or Chaos Mesh in-cluster): deliberately kills a random Order Service pod, or injects latency into the Payment Service's calls, IN A CONTROLLED WINDOW, to verify the circuit breakers (Section 10.3), bulkheads (Section 10.4), and PodDisruptionBudget (Section 12.6) behave as designed ΓÇö rather than discovering their behavior for the first time during a real incident.
≡ƒÆí Both load and chaos tests run against staging (or a dedicated pre-prod environment), never directly against production ΓÇö the goal is to find the breaking point and the failure behavior on purpose, on a schedule the team controls, which is the entire value of doing this proactively rather than waiting for an actual outage to teach the same lesson.

15. Logging & Monitoring in Production
Once services are distributed across many pods, you can't just SSH in and tail a log file. Production systems centralize both metrics (numbers over time) and logs (discrete events) so an engineer can answer "what's happening right now" and "what happened during that incident" from one place.
15.1 Metrics: Prometheus + Grafana
Each service exposes a /metrics HTTP endpoint (via prom-client in Node.js). Prometheus scrapes this endpoint on a schedule and stores the time-series data; Grafana queries Prometheus to render dashboards.
A useful mental model for what to measure is the RED method for services (Rate, Errors, Duration) and the USE method for resources (Utilization, Saturation, Errors) ΓÇö e.g., for Order Service: request rate, error rate, p95 latency (RED); and CPU/memory utilization, queue depth (USE).
Order Service: requests/sec, error rate by status code, p95/p99 latency, DB connection pool saturation.
Kafka consumers: consumer lag per partition (how far behind real-time a consumer is) ΓÇö the single most important Kafka health metric.
Databases: query latency, active connections, replication lag.
15.2 Logging: Structured Logs + EFK Stack
Every service logs structured JSON (via Pino) rather than free-text lines, so logs are machine-parseable. Each pod's stdout is collected by a Fluent Bit DaemonSet running on every Kubernetes node, shipped to Elasticsearch, and browsed/searched in Kibana (the "EFK" stack ΓÇö an ELK stack using Fluent Bit instead of Logstash).
A structured log line ΓÇö searching Kibana for correlationId: c4e1f2a0-... surfaces this exact request's journey across every service it touched.
15.3 Alerting
Prometheus's Alertmanager evaluates rules against the collected metrics (e.g., "error rate > 5% for 5 minutes" or "Kafka consumer lag > 10,000 messages") and routes notifications to Slack or PagerDuty, so humans are pulled in only when a threshold is actually breached ΓÇö not by watching dashboards all day.
15.4 Distributed Tracing
Metrics tell you THAT something is slow; traces tell you WHERE. Tools like OpenTelemetry (instrumenting each service) combined with Jaeger or Grafana Tempo let you visualize one request as a timeline of spans across the Gateway, Order Service, its database call, and even the asynchronous hop through Kafka to Payment ΓÇö turning the correlation ID from Section 10.7 into an actual visual waterfall.
15.5 SLOs, SLIs & Error Budgets
15.6 Business Metrics & Reconciliation Signals

Dashboards should include business-level signals in addition to infrastructure metrics: checkout acceptance rate, payment success rate, inventory reservation failure rate, expired reservations, refund backlog, Kafka consumer lag by critical group, outbox backlog/age, and orders stuck in intermediate states beyond their expected duration.
Alerting should distinguish infrastructure incidents from business-correctness incidents. A growing outbox backlog or orders stuck in PAYMENT_PENDING can indicate a distributed workflow failure even when HTTP error rates remain low.
Section 2.2 stated availability and latency targets. This section is how those targets are made operational, rather than aspirational numbers nobody checks.
The error budget is what turns Section 14's canary rollout (Figure 9) from a vague safety measure into a concrete decision rule: if a canary deploy would burn through a large fraction of the remaining monthly error budget in a short window, Argo Rollouts' automated analysis blocks the promotion ΓÇö the same mechanism protects against both a genuinely broken deploy and a slow accumulation of minor regressions that individually look acceptable.
When the error budget is healthy (little of it spent), the team has room to ship faster and take on riskier changes.
When the error budget is nearly exhausted, the team's priority explicitly shifts to reliability work over new features until it recovers ΓÇö this is what stops "launch velocity" and "reliability" from being a purely political argument, by giving both sides a shared, pre-agreed number.

18. Putting It All Together: One Order, Start to Finish
Browser sends POST /api/v1/orders. It hits the Ingress ΓåÆ API Gateway (Figure 1), never the Order Service directly.
The pod's middleware ΓåÆ controller ΓåÆ validation ΓåÆ service layer validates the cart, requests the current product price from the Product Catalog Service, calculates the order total, and writes orders + order_items + an outbox_events row in ONE Postgres transaction (Figure 4). Inventory remains the source of truth for stock; Order Service does not read the Inventory database directly.
A relay process reads the new outbox row and publishes order.created to Kafka, keyed by order_id (Section 8.4) ΓÇö guaranteeing the event is never lost relative to the DB write.
Independently, Inventory Service consumes order.created and attempts the reservation. Only after inventory.reserved does Payment Service charge the customer and publish payment.completed (or payment.failed). This sequencing avoids charging for an order that could not reserve stock.
If Payment fails, Inventory consumes payment.failed and releases its reservation; Order Service moves the order to CANCELLED. If a later fulfillment failure occurs after payment has succeeded, the design must issue a compensating refund and record the refund outcome for reconciliation.
This is the core shape of the event-driven flow: the synchronous request only accepts the order, while inventory, payment, fulfillment, notifications and compensations proceed as independently retryable state transitions.

Individual sections above called out edge cases local to that topic. This section collects the ones that only appear when several parts of the system interact ΓÇö the cases that actually show up in production incident reviews.
20. Common Pitfalls in Production Systems
Sharing a database or a shared models library across services ΓÇö quietly recreates a monolith.
Chaining synchronous calls 3+ services deep ΓÇö one slow link causes a cascading failure.
Non-idempotent Kafka/queue consumers ΓÇö duplicate delivery is normal, not an edge case.
Publishing to Kafka before the DB transaction commits (or vice versa without an outbox) ΓÇö the classic dual-write bug (Section 9.3).
Skewed Kafka partition keys (e.g., keying by a low-cardinality field) ΓÇö creates "hot" partitions that one consumer can't keep up with.
No resource requests/limits on Kubernetes pods ΓÇö one noisy-neighbor pod can starve others on the same node.
Ignoring consumer lag as a metric ΓÇö a slowly growing lag is often the first sign of trouble, long before errors appear.
Skipping correlation IDs early ΓÇö debugging a multi-service, part-sync-part-async bug without them is extremely painful.
Reusing a fresh Idempotency-Key on every retry (instead of the same key) ΓÇö silently defeats the entire idempotency mechanism in Section 11.
Mixing server-cache data and client-only UI state in one frontend store ΓÇö recreates cache-invalidation bugs that TanStack Query already solves (Section 4.2).
Deploying straight to production without a canary stage ΓÇö the first signal of a bad deploy becomes a customer complaint instead of an automated rollback (Section 14.2).
20.1 Architecture Decision Checklist
Every cross-service workflow has an explicit state machine, timeout, retry policy, compensation path, and reconciliation path.
No service reads another service's database directly; synchronous APIs and domain events are the integration boundaries.
Every externally triggered mutation has an idempotency strategy, including payment, refunds, webhooks, and important consumer side effects.
Each production SLO has a measurable SLI, alert threshold, owner, and a tested runbook.
Infrastructure and application rollouts support safe rollback, backward-compatible migrations, and schema/event compatibility checks.
21. Key Takeaways & Production Readiness
The architecture is complete when correctness, security, operability and scale are treated as one system rather than isolated concerns.

Each cross-service workflow has an explicit state machine, timeout, retry policy, compensation path and reconciliation path.

Appendix D: Security Architecture ΓÇö Defense in Depth
Security controls appear throughout this document wherever they're most relevant to the topic at hand ΓÇö Section 2.2's NFRs, Section 4.6's token storage, Section 10.8's network policies, Section 13's IAM, Appendix C's threat model. This appendix pulls the full picture together into one place, layer by layer, from the browser to the database, so the question "how is X actually secured end-to-end" has one answer to point to rather than six scattered ones.
D.1 The Model: Zero Trust, Defense in Depth
The guiding principle is Zero Trust: no request is trusted by virtue of WHERE it came from (inside the VPC, inside the cluster) ΓÇö every hop authenticates and authorizes independently, and every layer assumes the layer before it could fail. This is why the controls below overlap rather than forming a single chain: a gap in one layer is still caught by the next.
≡ƒÆí Read this table as independent layers, not a single wall: an attacker who somehow bypasses the WAF still hits JWT validation at the Gateway; one who somehow forges a JWT still can't move laterally between services without a valid mesh identity (D.4); one who compromises a pod still can't read another service's database credentials (D.6/D.8's least-privilege scoping).
D.2 Frontend / Client Security
Section 4.6 already covers where tokens live in the browser; this section covers the other client-side risks a modern React SPA has to defend against.
D.3 Edge & API Gateway Security
Everything from the internet lands here before it ever reaches a service, which is why this layer carries the broadest, coarsest controls.
ΓÇóΓÇéTLS termination happens at CloudFront/ALB using ACM-managed certificates with automatic renewal ΓÇö no service ever handles a raw, unencrypted request from the public internet.
ΓÇóΓÇéAWS WAF (Section 13.1) filters common attack signatures (SQLi, XSS payloads, known bad IP reputation lists) before a request reaches the ALB, and rate-based rules throttle a single IP's request rate independently of the Gateway's own per-user rate limiting (Section 10.1).
ΓÇóΓÇéThe Gateway validates the JWT's signature, issuer, audience, and expiry on every request ΓÇö not just its presence ΓÇö before proxying anywhere, and rejects malformed request bodies against a schema (Section 3's API contracts) before they reach business logic.
ΓÇóΓÇéInternal service addresses (order-service.default.svc.cluster.local) are never resolvable from outside the cluster ΓÇö the Gateway is the only component with a public-facing route, which is what makes the internal Zero Trust layer in D.4 meaningful rather than redundant.
D.4 Service-to-Service Security: Securing Communication Between Microservices
This is the layer most system designs leave implicit ΓÇö "it's all inside our VPC, so it's trusted" ΓÇö which is exactly the assumption Zero Trust rejects. Section 10.8 and 12.6 already establish NetworkPolicies as a coarse allow-list ("only pods labeled api-gateway may open a connection to order-service on port 3003"). That controls WHICH pods can connect. It says nothing about WHO is on each end of that connection, or whether the traffic itself could be read or altered by anything sitting on the network path. Two further controls close that gap.
D.4.1 Mutual TLS via a Service Mesh
A service mesh (Istio or Linkerd) is installed alongside Kubernetes and injects a lightweight proxy (a "sidecar") into every pod. All traffic in and out of a pod's application container is transparently routed through its sidecar ΓÇö the application code itself makes plain, unencrypted HTTP calls exactly as shown in Section 13's code samples, and never has to know encryption is happening.

Figure 11 ΓÇö Order Service's sidecar and Payment Service's sidecar each hold a short-lived certificate proving their identity; traffic between the two sidecars is encrypted and mutually authenticated, while each application container only ever talks to its own local sidecar in plain HTTP.
ΓÇóΓÇéEvery workload gets a cryptographic identity (a SPIFFE ID, e.g. spiffe://cluster/order-service) issued by the mesh's certificate authority ΓÇö NOT an IP address or a Kubernetes label, which can be spoofed far more easily than a private key.
ΓÇóΓÇéCertificates are short-lived (rotated automatically, often hourly) ΓÇö a leaked certificate is a much smaller, self-healing window of exposure than the multi-year TLS certificates typically used for public-facing endpoints.
ΓÇóΓÇéBecause encryption happens at the sidecar, application code (the Section 13 Express examples) needs zero changes to gain mTLS ΓÇö this is precisely why the mesh is the practical way to add encryption-in-transit across dozens of internal service-to-service calls without touching every codebase.
D.4.2 Service-Level Authorization (Not Just Authentication)
mTLS answers "who is calling" cryptographically. It does not answer "should this caller be allowed to call this specific endpoint" ΓÇö that is a separate, explicit authorization policy, enforced at the mesh layer independent of whatever the application code itself checks.
≡ƒÆí This is the mesh-level analogue of IRSA (Section 13.19): IRSA scopes what a service can do against AWS APIs; the mesh AuthorizationPolicy scopes what a service can do against OTHER SERVICES. A compromised Notification Service pod (Appendix C's Elevation-of-Privilege row) is blocked twice over ΓÇö once by the NetworkPolicy that never opens a route to it, and again by this policy even if it somehow reached Payment's network address.
D.4.3 Propagating User Identity Across Internal Calls
A subtlety many designs miss: once the Gateway validates a shopper's JWT, how does Order Service ΓÇö several hops and possibly a Kafka event later ΓÇö know which authenticated user this action is actually for, without re-trusting a client-supplied user ID?
ΓÇóΓÇéThe Gateway forwards the original, still-valid JWT (or a short-lived internal token derived from it, carrying only the user ID and roles, not the full external claims) as an internal header on the downstream call ΓÇö internal services verify this token's signature exactly as the Gateway does, rather than trusting an unsigned X-User-Id header that any caller could set arbitrarily.
ΓÇóΓÇéFor asynchronous flows, the user ID travels as part of the signed event payload (Section 8's order.created event already carries the authenticated order owner), so a consumer never has to "look up" who a request was for from an untrusted source.
D.5 Kafka / Event Backbone Security
The event backbone (Section 8) carries order, payment, and inventory data between services and deserves the same authentication and authorization rigor as any synchronous call.
D.6 Data-at-Rest & Database Security
ΓÇóΓÇéEvery RDS instance, DocumentDB cluster, and ElastiCache replication group is encrypted at rest with a KMS customer-managed key (Section 13.11's backups inherit this encryption automatically).
ΓÇóΓÇéEach service connects to its database with its OWN least-privilege database user ΓÇö Order Service's DB user can read/write only the order_db schema's tables and cannot even see the payment_db schema exists, enforced at the PostgreSQL grant level, not just at the network layer (Section 6's database-per-service rule, made concrete).
ΓÇóΓÇéReporting/analytics queries connect through a separate, read-only database user pointed at a read replica (Section 9.4) ΓÇö a compromised reporting credential can leak data but can never modify it.
ΓÇóΓÇéPII fields (shipping address, phone number) are protected by RDS's encryption at rest as a baseline; where a specific field is highly sensitive, application-level field encryption (encrypting before INSERT, decrypting only in the service that owns the data) is used so even a raw database dump or a misconfigured snapshot share doesn't expose it in plaintext.
ΓÇóΓÇéCard data specifically never reaches this system's own database in any form, encrypted or not ΓÇö Payment forwards directly to Stripe/PayPal (Section 2.2's PCI-DSS scope note) ΓÇö the strongest possible mitigation for that data class is simply not storing it at all.

E.2 CAP Theorem: Where This System Sits
The CAP theorem states that a distributed system can only guarantee two of three properties during a network partition: Consistency (every read sees the latest write), Availability (every request gets a response), and Partition tolerance (the system keeps working despite network failures between nodes). Partition tolerance isn't really optional for a multi-AZ, multi-service system (Section 13's VPC spans two AZs, and network partitions between them, however rare, must be survivable) ΓÇö so the real, everyday choice this system makes repeatedly is Consistency vs. Availability, not whether to have partition tolerance at all.
≡ƒÆí This is why Section 9.5 explicitly chose a Saga over a distributed two-phase-commit (2PC) transaction spanning Order and Payment's databases: 2PC would push this system toward CP across services (blocking until every participant confirms), which conflicts with Section 2.2's availability target far more than the eventual consistency a Saga accepts.
